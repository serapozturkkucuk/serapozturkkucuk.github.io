Object relationships

The problemChoosing the wrong relationship is hard to undo. It decides who owns the child record, who can see it, what happens when the parent is deleted, and whether you can total the children.
What I madeA decision map from "how many on each side?" to the right relationship, with a real example for each, and the rules I check before changing a relationship type.

Owner and sharingThe child has its own owner and sharingThe child has no owner; it follows the parent
Delete the parentThe field is cleared, or the delete is blockedThe children are deleted too (and restored with it)
Roll-up summary fieldsNoYes, on the master: COUNT, SUM, MIN, MAX

02 · Security and access

Security and sharing

The problem"I can't see this record" is the most common ticket an admin gets. The cause can be in three different places, and each is fixed with a different tool.
What I madeA map of the three checks every user must pass, a check order for troubleshooting, and Harbourline's requests matched to the right tool.
Built and tested in the org
  • Org-wide defaults: Opportunity Private, Account and Case Public Read Only, Contact Controlled by Parent, Training Session Public Read Only
  • Role hierarchy by department; criteria-based sharing rule (Closed Won deals to the service team, Read Only); account team on Northgate
  • Login As results: Priya sees her 3 deals plus Northgate's; Leo only Northgate's; Marcus sees Priya's; Ada the 8 Closed Won deals, read only
  • Found while testing: Ada saw no deals at all, because her profile had no Read on Opportunity. A sharing rule can't open an object the profile can't read
Permissions: what a user can do Sharing: which records they reach Good to know

A user can't see a record: check in this order

  1. Log inIs the user active, inside the login IP ranges and login hours?
  2. ObjectDoes the profile or a permission set give Read on the object?
  3. FieldIf a field is missing, does field-level security make it visible?
  4. RecordDoes OWD, the role hierarchy, a sharing rule or a manual share give access to this record?

The "Sharing" button on a record shows exactly who has access and why, which is the quickest way to check step 4.

06 · Automation

Choosing an automation tool

The problemFlow can do almost anything, so it gets used for jobs a simpler tool does better and that are easier to maintain.
What I madeA check to run before building any flow: match the business need to the simplest tool, using the words people actually say. Every example is built in the Harbourline org.

Only the last row needs a flow. The others are simpler, built with clicks, and easier for the next admin to understand.

Business needClue wordsWhy it isn't a flow
Store or link datastore, keep, link, belongs toIt's the data model. Nothing needs to happen automatically.
Calculate a value to showshow, display, calculate, combineA formula only works out a value and shows it. It never creates records or sends emails.
Add up child recordstotal, count, sum of childrenA roll-up summary field does it with no automation, if the relationship is master-detail.
Stop a bad saveblock, prevent, must not, only allowA validation rule only says no. It does nothing else.
A button with a short formbutton, log a call, new record from hereA Quick Action has no decisions. It can launch a flow if logic is needed.
Needs someone to say yes or noapprove, reject, must be approvedOnly an Approval Process has approve and reject steps.
Must happen by itself, with logicautomatically, when, if, create, email, updateThis one is a flow.

Flow design

The problemA business asks for "something automatic." The admin has to pick the flow type, the save timing and the fewest elements that do the job.
What I madeA four-question decision chart, from the trigger to the extra elements, with practical notes, then worked examples that follow the chart to a finished flow.
Question Answer Good to know

The record that starts a record-triggered flow is already in the flow with all its fields, so Get Records is only needed for other records. Every flow was tested on the path where it should act and the path where it shouldn't: a second won deal for Northgate created no duplicate Building, and 100 test Cases for Standard customers sent no alerts.

Worked example with a loop study example

Request: a button on the Account page sets Priority to High on that Account's open Cases (for example, Northgate Logistics), but only when the Subject contains "urgent".

1. What starts it?A user clicks a button, so it's a screen flow
2. Which records?Other records (the Cases), so no save timing to choose
3. How many?Many, each with its own answer, so a Loop
4. ExtrasGet Records first, and a Decision inside the loop
  1. 01Get RecordsFind the Account's open Cases
  2. 02DecisionAny Cases found? If not, stop here
  3. 03LoopGo through the Cases one at a time
  4. 04DecisionDoes this Case's Subject contain "urgent"?
  5. 05AssignmentSet Priority to High and add the Case to a list called casesToUpdate
  6. 06Update RecordsAfter the last Case, save casesToUpdate in one go

If every open Case should become High, with no urgent check, skip the loop: one Update Records with a filter does it in a single step. Never put Get, Create, Update or Delete Records inside the loop.
